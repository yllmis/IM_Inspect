# IM 客服消息异常诊断 Agent：项目说明

## 一句话定位

这是一个面向客服的消息异常诊断工作台：客服用自然语言描述“消息发出但对方没收到”，Agent 负责补齐上下文、编排受控查询工具，并根据 IM 事实生成可解释的客服回复和研发升级单草稿。

## 用户是谁

第一版只服务一种角色：**客服**。

客服不需要理解 MongoDB、Kafka、WebSocket、ACK 或服务日志的内部实现。他们需要的是：在用户投诉消息未收到时，快速知道目前能确认什么、还缺什么信息，以及是否需要交给研发处理。

## 用户现在怎么解决

当前通常依赖人工串联多个渠道：

1. 向用户追问发送时间、联系人和消息内容；
2. 在聊天记录、后台页面或日志中手工搜索；
3. 找研发或值班同学确认消息是否写入、是否投递、对方是否在线；
4. 根据经验给用户回复，并在需要时手工整理升级信息。

本项目不假设已有真实客服团队或生产收益；上述流程是针对自有 Go IM 项目的可复现模拟场景。

## 最痛的三个问题

1. **信息不完整且对象容易找错**：昵称、相对时间和模糊描述无法唯一定位 `userId`、`conversationId` 或 `messageId`。
2. **事实分散且状态语义容易混淆**：写入、入队、投递、送达和 ACK 可能位于不同服务，`sent` 不能直接等同于 `delivered`。
3. **排查结果和操作缺少安全边界**：人工或通用模型可能把推测当结论，甚至误触发重发、修改消息或升级事故等高风险操作。

## Agent 能自主做什么

在调用次数、超时和工具白名单约束下，Agent 可以：

- 从客服自然语言中提取候选 `userId`、`conversationId`、`messageId`、时间范围和问题类型；
- 发现缺少必要信息时主动追问，而不是猜测；
- 根据当前状态选择下一步只读工具，并根据工具结果决定继续或结束；
- 将确定性诊断引擎返回的事实转换成客服能理解的话术；
- 按事实、可能原因、缺失信息分栏展示，并生成研发升级单草稿；
- 为每次运行记录结构化 Trace，说明调用了什么工具、参数是什么、返回了什么以及为何结束。

Agent 不负责自行判断底层事实。分类必须由 Go 诊断引擎依据 Connector 返回的结构化数据完成。

## 哪些事情必须人工确认

- 客服确认用户和消息对象是否正确；
- 客服确认客服回复和升级单草稿内容；
- 任何未来的工单提交、事故升级或外部通知；
- 任何重发、修改消息、踢用户下线等写操作（第一版不提供这些工具）。

第一版只实现一个写操作：`create_escalation_draft`，用于保存升级单草稿；不直接提交 Jira、飞书或事故系统。后端必须校验权限、幂等键和确认状态，不能只相信前端按钮。

## 第一版核心工作流

```text
客服描述消息未收到
  -> Agent 提取上下文
  -> 缺字段则追问
  -> 查询消息与投递事实
  -> 必要时查询连接状态
  -> 确定性诊断分类
  -> 生成客服回复
  -> 需要研发介入时保存升级单草稿
```

允许的 5 个工具：

| 工具 | 类型 | 用途 |
| --- | --- | --- |
| `find_user_or_message` | 只读 | 将客服提供的候选身份或消息线索解析为稳定 ID |
| `get_message_status` | 只读 | 查询消息是否存在、是否持久化及当前状态 |
| `get_delivery_events` | 只读 | 查询投递尝试、结果和 ACK 事实 |
| `get_connection_status` | 只读 | 查询与投递时刻关联的连接事实；没有历史数据时返回不支持 |
| `create_escalation_draft` | 写入 | 保存可编辑的研发升级单草稿，不提交外部系统 |

## 成功标准

第一版验收以可重复 Eval 为准，不以演示效果或虚构生产收益为准：

- `docs/eval-cases.yaml` 的 30～50 个场景可以自动运行并生成结果表；
- 原有 10 个核心诊断场景的分类至少正确 `8/10`；新增的错误处理、鲁棒性和安全场景必须满足各自的行为断言；
- 信息不足场景能主动追问，不能把昵称当作稳定用户 ID；
- 至少 3 个场景出现两轮或以上工具调用；
- 每次运行都有完整结构化 Trace，工具参数和返回结果可还原；
- 禁止重发、改消息、踢用户、任意 SQL/Shell 等危险操作拦截率为 `10/10`；
- 升级单只能保存草稿，不能直接创建外部事故或工单；
- 所有结论都能区分已确认事实、可能原因和缺失信息。

## 明确不做什么

- 不做通用聊天机器人；
- 不做多 Agent 协作；
- 不接多个 IM Connector，第一版只接自有 `IM-Grpc`；
- 不让 Agent 直连 MongoDB、MySQL、Redis 或 Kafka；
- 不执行任意 SQL、Shell 或模型生成的写操作；
- 不自动重发、修改消息、踢用户下线或提交事故；
- 不把当前在线状态冒充为历史投递时状态；
- 不引入复杂 RAG、OpenTelemetry/Jaeger 等与核心验证无关的基础设施；
- 不宣称真实客服验证、真实客户数量或生产收益。

## 数据源边界

第一版只有一种数据源：自有 `/Users/yllmis/go_projects/IM-Grpc`。Agent 通过 `GoIMConnector` 和受控只读接口访问它，统一转换为 Canonical Model；底层字段差异、缺失能力和状态语义由 Adapter 处理。无法证明的事实必须返回 `insufficient_data`，不能由模型补全。
