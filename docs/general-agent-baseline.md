# 通用 Agent 基线压力测试

## 目的

在继续开发前，先把“IM 客服消息异常诊断 Agent”的需求交给通用编码 Agent，检查项目核心价值是否只是代码生成、Tool Calling 或聊天总结。如果通用 Agent 在没有领域数据和安全边界的情况下就能完成核心价值，说明选题需要收窄或加深。

本文记录测试协议和当前基线观察。当前没有独立调用 ChatGPT、Claude Code 的运行环境，因此不会把推测写成它们的实测结果；后续拿到对应环境后，使用同一提示词和同一仓库补录结果。基线结果使用评测集扩展前的 10 个核心场景快照，当前正式评测集已扩展为 24 个场景。

已完成的当前对话 Codex 基线结果见：`docs/general-agent-baseline-result-codex.md`。

## 统一测试提示词

将以下内容原样交给每个通用编码 Agent：

```text
你要实现一个“IM 客服消息异常诊断 Agent”。

目标用户是客服和一线值班人员。客服输入自然语言，例如“消息发出去了但对方没收到”。系统需要：
1. 提取 userId、conversationId、messageId、时间范围和问题类型；
2. 信息不足时追问；
3. 通过受控工具查询消息、投递事件和连接事实；
4. 由确定性诊断逻辑输出 message_not_found、write_failed、not_delivered、receiver_offline、ack_timeout、delivered 或 insufficient_data；
5. 生成客服回复和研发升级单草稿。

约束：
- 不允许 Agent 直接访问数据库、执行任意 SQL/Shell；
- 不允许自动重发消息、修改消息、踢用户下线或直接提交事故；
- 升级单只能先生成草稿，提交必须由后端确认；
- 输出必须区分已确认事实、可能原因和缺失信息；
- 需要结构化 Trace 和可运行 Eval。

请在当前仓库中实现尽可能完整的版本，并说明：
- 你实际完成了什么；
- 需要哪些外部数据、接口、凭证或业务语义；
- 哪些操作存在安全风险；
- 哪些能力不能可靠持续运行；
- 哪些结果会因模型或输入而不稳定；
- 为什么用户需要这个产品，而不是直接使用通用 Agent。
不要虚构真实客户、生产收益或不存在的 IM 接口。
```

并逐项回答：

| 观察项 | 证据要求 |
| --- | --- |
| 能直接完成什么 | 文件、测试命令和实际输出 |
| 缺少什么数据 | 缺失的字段、状态语义、事件或权限 |
| 什么操作不安全 | 具体工具、写操作、权限绕过或数据泄露路径 |

| 为什么需要本产品 | 通用 Agent 无法替代的领域边界和可验证能力 |

## 当前 Codex 基线观察

这是本次对话中已经实际发生、可由仓库内容复核的结果，不是对其他模型的推断。

### 能直接完成

- 检查工作区和外部 `IM-Grpc` 项目目录。
- 阅读 README、Go struct、RPC proto、MongoDB model 和 WebSocket/Kafka 消息流程。
- 根据需求起草状态机和首批 10 个核心 Eval 场景。
- 设计统一 Canonical Model、Connector Interface 和 Fake Connector 的边界。
- 生成确定性诊断引擎、Tool Service、Trace、Eval Runner 的代码骨架（尚未在本仓库实现）。

### 明确缺少的数据

`IM-Grpc` 当前能确认用户、会话和聊天记录查询，但缺少可验证的诊断事实：

- 独立的 `DeliveryEvent` 模型和查询接口；
- 投递发生时的历史连接状态；
- 持久化失败事件及错误码；
- Kafka 入队、消费、推送、ACK 的关联 ID；
- 明确维护的消息状态迁移；
- 可重复的故障注入 fixture。

当前 WebSocket 的 `sent` ACK 只能说明请求进入处理链路，不能直接证明接收方收到消息。

### 不安全的操作

- 让模型直连 MongoDB、MySQL、Redis 或 Kafka；
- 执行模型生成的任意 SQL/Shell；
- 让 Agent 自动重发、修改消息、踢用户下线；
- 只依赖前端按钮状态提交升级单；
- 将用户输入或日志中的指令当成系统指令执行；
- 将 `displayName`、当前在线状态或模型推测写成稳定事实。

### 无法可靠持续运行的能力

- 没有持久化状态和幂等键的多轮 Agent Loop；
- 没有超时、调用上限和取消机制的工具调用；
- 依赖实时 Redis 在线状态推断历史投递状态；
- 依赖模型自行维护长时间故障排查上下文；
- 没有可观测 Trace 的后台重试和异步消费链路。

### 结果容易不稳定的地方

- 从模糊昵称或相对时间提取唯一用户和消息；
- 在多个匹配结果中选择对象；
- 将 `sent`、`delivered`、`acknowledged` 混为一谈；
- 在证据不足时猜测根因；
- 工具调用顺序、是否继续查询和最终客服措辞；
- 遇到提示词注入时是否尝试执行日志中的命令。

## 产品必要性判断

通用 Agent 可以快速生成代码、解释日志、设计工具 Schema，甚至在有 Mock 数据时跑通一次演示。但它无法凭空获得以下能力：

1. 访问并理解某个 IM 的真实数据语义；
2. 证明消息状态、投递事件和 ACK 的因果关系；
3. 在证据不足时稳定返回 `insufficient_data`；
4. 通过 Connector 隔离不同 IM 的字段和能力差异；
5. 在真实权限边界内阻止危险写操作；
6. 用固定故障注入和 Eval 数字持续验证分类质量；
7. 保留可审计 Trace，让客服和研发知道每一步为何发生。

因此产品核心不是“让模型回答消息为什么没收到”，而是：

> 将具体 IM 的事实数据、安全策略、确定性诊断和 Agent 的自然语言交互组合成可验证的客服排障流程。

只有在后续 Eval 证明通用 Agent 通过简单 Prompt + Mock 工具即可达到同等准确率时，才需要重新收窄问题或增加更深的领域约束。

## 后续实测步骤

1. 固定一个 commit，分别在 ChatGPT、Codex、Claude Code 中使用上面的提示词。
2. 限制 20 分钟，记录所有文件变更、命令、测试输出和未完成事项。
3. 用固定版本的 10 个核心场景运行基线，不接受只展示成功 Demo；产品 Agent 验收时再运行当前 24 个场景。
4. 对每个失败记录“模型错误、数据缺失、接口缺失还是安全策略缺失”。
5. 将实测数字补回本文件，再决定是否继续当前选题和架构。
